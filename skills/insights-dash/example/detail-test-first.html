Focus — Test-First Discipline
Write tests first
Implementation without tests is a guess. Tests make Claude's feedback loop instant.
40%

Why it matters

  • Tests written after implementation tend to match the code, not the requirement — they confirm the code runs, not that it works
  • Claude can enter an autonomous fix loop when tests exist — without them it must ask you for feedback after every change
  • Debugging is faster when you know exactly which assertion is failing

The pattern

What it looks like without test-first:

New feature

You said "implement X." Claude built it, then you found edge cases in manual testing. The fix took longer than the original build.

Refactor

You said "refactor Y." Claude moved things around. Nothing broke immediately, but a regression surfaced two days later with no clear cause.

How to build the habit

  1. Start every task with failing tests Ask Claude to write failing tests first — describe the acceptance criteria, not the implementation. Review the tests before any code is written.
  2. Tell Claude the loop "Write tests, then implement, then run tests, loop until green." Claude can run this autonomously.
  3. Track it per PR In your growth-rules.md, count how many PRs this period had tests written before implementation.

Copyable prompts

TDD loop prompt:

Phase 1: Write a complete test file for [feature]. Tests should fail. Show me the tests and wait for my approval before writing any implementation. Phase 2: After approval, implement until all tests pass. Run tests after every change. Do not ask questions — if blocked, document the blocker and try a different approach.

Add to AGENTS.md to make it permanent:

## Test-First Discipline - Write failing tests before implementing any feature or fix - Do not modify test assertions to make tests pass — fix the implementation - Run the full test suite before declaring a task done
